# ADR-002: Segmentación de Redes Docker y Proxy Inverso con Nginx como Punto Único de Entrada

## 1. Contexto y Problema

En la arquitectura distribuida de **CampusBite** coexisten 8 contenedores internos con responsabilidades diferenciadas: la API transaccional escalada (`api_pedidos` x2), la base de datos relacional (`campusbite_postgres`), el broker de mensajería (`campusbite_kafka`) y cinco microservicios consumidores (`cocina`, `estadisticas`, `notificaciones`, `caja` y `facturacion`).

Exponer directamente los puertos de cada servicio hacia el host (`5000`, `5001`, `5002`, `5432`, `8765`, `9092`) genera tres riesgos arquitectónicos graves:
1. **Superficie de ataque expuesta:** Cualquier cliente externo podría intentar conectarse directamente a PostgreSQL (`5432`) o publicar eventos falsos en Kafka (`9092`) sin pasar por validaciones de negocio.
2. **Acoplamiento de clientes:** Los consumidores externos (web/móvil de estudiantes, panel de cocina y dashboard administrativo) tendrían que conocer múltiples puertos y direcciones IP individuales de cada réplica.
3. **Ausencia de balanceo de carga:** Sin un intermediario HTTP, el tráfico entrante no podría distribuirse dinámicamente entre las réplicas de `api_pedidos`.

---

## 2. Decisión Arquitectónica

Se decide implementar una topología de **red de dos niveles** acompañada de un **Proxy Inverso y Balanceador de Carga** basado en **Nginx 1.27 (`nginx:1.27-alpine`)**:

1. **Red externa (`frontend_net`):** Red tipo `bridge` a la que únicamente se conectan el host y el contenedor `campusbite_proxy`, exponiendo exclusivamente el puerto **`8080:80`** (`PROXY_PORT`).
2. **Red privada aislada (`backend_net`):** Red tipo `bridge` configurada con la directiva **`internal: true`**, donde residen todos los microservicios, Kafka y PostgreSQL sin ningún mapeo de puertos (`ports:`) hacia el exterior. El contenedor `campusbite_proxy` actúa como puente controlado al pertenecer a ambas redes (`frontend_net` y `backend_net`).
3. **Enrutamiento centralizado y soporte WebSocket:** Nginx unifica todos los endpoints bajo un único origen (`http://localhost:8080`):
   * `/pedidos` y `/health` $\rightarrow$ `http://api_pedidos:5000` (balanceo automático *round-robin* entre las 2 réplicas).
   * `/cocina` $\rightarrow$ `http://ms_cocina:5001`.
   * `/estadisticas` $\rightarrow$ `http://ms_estadisticas:5002`.
   * `/ws` $\rightarrow$ `http://ms_notificaciones:8765` (con cabeceras `Upgrade` y `Connection "upgrade"` para HTTP/1.1).
4. **Resolución DNS dinámica en Nginx:** Se configura `resolver 127.0.0.11 valid=5s;` junto con variables `set $upstream ...` dentro de cada bloque `location`, obligando a Nginx a re-resolver dinámicamente las IPs de los contenedores ante escalados o reinicios sin fallar al arrancar si un upstream tarda unos segundos en estar listo.

---

## 3. Alternativas Consideradas

* **Exponer cada microservicio en un puerto distinto del host (`5000`–`8765`) sobre la red `default` de Docker Compose:**
  * *Descartada:* Elimina el aislamiento de red (dejando puertos internos accesibles desde fuera), impide balancear múltiples réplicas de `api_pedidos` en un mismo puerto y obliga al cliente a gestionar múltiples URLs.
* **Utilizar un API Gateway pesado (Kong, Traefik o Spring Cloud Gateway):**
  * *Descartada:* Introduce un consumo elevado de memoria RAM y complejidad de configuración innecesaria para el alcance académico del proyecto; Nginx en Alpine pesa ~40 MB, soporta nativamente balanceo HTTP y túneles WebSocket, y se configura de forma declarativa en un único archivo `nginx.conf`.
* **Configurar `upstream` estáticos en `nginx.conf` sin `resolver 127.0.0.11`:**
  * *Descartada:* Nginx resuelve los nombres de host estáticos únicamente al iniciar; si una réplica de `api_pedidos` se recrea y cambia su IP interna en `backend_net`, Nginx seguiría enviando tráfico a la IP antigua provocando errores `502 Bad Gateway`.

---

## 4. Consecuencias

### Positivas
* **Aislamiento verificado:** Ningún servicio interno ni la base de datos responde a conexiones TCP directas desde el host (verificado con `Test-NetConnection` sobre los puertos `5432` y `5001`.
* **Punto único de entrada:** Toda la comunicación externa fluye de manera controlada a través del puerto `8080`, simplificando futuras políticas de TLS/HTTPS, *rate limiting* o autenticación centralizada.
* **Escalado transparente:** Es posible aumentar `API_REPLICAS` en el archivo `.env` sin modificar la configuración de Nginx ni las rutas del cliente.

### Negativas / Compromisos (*Trade-offs*)
* **Punto único de entrada (*Single Point of Entry*):** Si `campusbite_proxy` se detiene, los clientes externos pierden acceso a todos los servicios aunque estos sigan saludables internamente; se mitiga configurando `restart: unless-stopped` y `depends_on` hacia los servicios críticos.
* **Salto adicional de red:** Cada petición atraviesa un *proxy hop* adicional antes de llegar al microservicio destino, agregando una sobrecarga inferior a 1 ms dentro de la red puente local de Docker.
